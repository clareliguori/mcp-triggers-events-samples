### Webhook Event Delivery

| Feature | Status | Notes |
|---------|--------|-------|
| POST to callback URL | ✅ | `deliverWebhookToSubscription` from SDK |
| Standard Webhooks `webhook-id` header | ✅ | Set to `eventId` |
| Standard Webhooks `webhook-timestamp` header | ✅ | Unix seconds |
| Standard Webhooks `webhook-signature` header | ✅ | `v1,<base64 HMAC-SHA256>` |
| `X-MCP-Subscription-Id` header | ✅ | Carried on every delivery |
| Body: `EventOccurrence` shape | ✅ | `{eventId, name, timestamp, data, cursor}` |
| Retry with exponential backoff | ✅ | 3 attempts (1s/5s/30s) in `sdk-deliver.ts` |
| Signature uses per-subscription secret | ✅ | Secret decrypted from DynamoDB per subscription |
| Receiver verifies signature before processing | ✅ | Webhook Receiver validates HMAC |
| Timestamp freshness (reject > 5 min) | ✅ | Replay window check in signature validation |
| `eventId` deduplication by receiver | ✅ | Agent deduplicates via `processedEventIds` in session metadata |
| `cursor` in delivery body (safe-to-persist watermark) | ⚠️ | A cursor is included but it's a synthetic event-specific cursor, not a watermark that advances past unacked events |
| Delivery suspension after repeated failures | ❌ | Events go to DLQ after max retries, but no `active: false` status |
| Secret rotation with dual-sign grace window | ❌ | Subscription Manager could rotate but dual-signing not implemented |

## Key Design Decisions Alignment

| Decision | Alignment | Notes |
|----------|-----------|-------|
| Three delivery modes | Partial | Only webhook implemented; design says "no mode subsumes another" — this project chose webhook because it fits the serverless wake/sleep pattern |
| Standard Webhooks signature scheme | ✅ | Full compliance with `v1,` HMAC signatures |
| One subscription per request | ✅ | Each `events/subscribe` call is for one event type |
| Client-supplied webhook secret | ✅ | Subscription Manager generates and supplies `whsec_` |
| Server holds no durable subscription state | ⚠️ | Design says "TTL'd soft state"; this project uses DynamoDB with TTL-based expiry (items auto-delete after `refreshBefore`), so subscriptions still expire if not refreshed — the semantics match the design, just backed by durable storage because Lambda can't hold in-memory state. The SDK fork contributes a `WebhookSubscriptionStore` interface so external stores can be plugged in; this project implements it with DynamoDB. |
| Webhook requires authenticated principal | ✅ | IAM auth on MCP server API Gateways |
| `https` required for callback URLs | ✅ | All endpoints are HTTPS |

## What This Project Demonstrates Beyond the Design

| Feature | Notes |
|---------|-------|
| Serverless (Lambda) MCP server deployment | Design assumes long-running servers; this shows how to implement with stateless Lambda + DynamoDB |
| `DynamoDBWebhookSubscriptionStore` | Implements the `WebhookSubscriptionStore` interface (contributed to the SDK fork) with DynamoDB, enabling serverless operation |
| Per-subscription KMS encryption of secrets | Client-side field encryption with per-table KMS keys and encryption context binding |
| Multi-customer routing via `X-MCP-Subscription-Id` | Design mentions the header for "routing"; this project fully implements subscription-to-customer resolution |
| Forward proxy pattern | Webhook Receiver + SQS acts as the "forward proxy" the design describes, buffering events for the agent |
| Conversation-as-accumulator | Events are injected into an LLM conversation history rather than stored in a database |

---

## Summary

This project is a **comprehensive implementation of the webhook delivery mode** of MCP Events. It demonstrates the full subscribe/deliver/refresh lifecycle with Standard Webhooks signatures, per-subscription client-supplied secrets, TTL-based expiry, and multi-tenant routing. It does not implement poll or push delivery modes, cursor-based replay, payload schemas, delivery status reporting, non-event control envelopes, endpoint verification, or SSRF prevention — features that are either irrelevant to the serverless webhook-only topology or not needed for a demo.
